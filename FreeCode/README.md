# FreeCode

وكيل برمجة بالذكاء الاصطناعي لسطح المكتب (فكرته مثل Cline / OpenCode)، يعمل على مفتاح **FreeLLMAPI** الموحد.
Electron + TypeScript، وبدون مكتبات وقت تشغيل إضافية (الواجهة مكتوبة من الصفر، و`esbuild` لتحزيمها فقط).

## التشغيل

يتطلب Node.js 20 أو أحدث.

```bash
npm install
npm start
```

## الإعداد (مرة واحدة)

من **الإعدادات** داخل التطبيق:

- **عنوان الخادم:** مثل `http://127.0.0.1:31415` (تُضاف `/v1` تلقائياً)
- **المفتاح الموحد:** `freellmapi-…` (يُخزَّن مشفّراً عبر نظام التشغيل عند توفر ذلك، ويمكن حذفه من زر «حذف المفتاح» في الإعدادات)
- **الموديل:** `freellmapi/auto`، أو اضغط "اختبار الاتصال" واختر من القائمة

ثم اختر مجلد المشروع وابدأ.

## الميزات

| **وكلاء فرعيون (`task`)** | يفوّض الوكيل الاستكشاف لوكلاء للقراءة فقط بسياق مستقل، ويعملون بالتوازي وتراهم يبثّون تقدمهم |

| **تحقق تلقائي بعد التعديل** | بعد كل تعديل يكتشف المشروع ويشغّل فحص الأنواع/الـ lint ويعيد الأخطاء للنموذج ليصلحها فوراً (يُضبط أو يُعطَّل من الإعدادات) |
| **عمليات خلفية** | يشغّل الوكيل خادم التطوير ويقرأ سجلاته ويوقفه (`start_process` / `process_output` / `stop_process`)، وتُقتل كلها عند الإغلاق |
| **خريطة المستودع** | استخراج رموز الملفات وترتيبها بأهميتها بترتيب الصفحات على رسم الاستيراد (مثل خريطة Aider)، تُضاف لسياق الوكيل فيفهم المشاريع الكبيرة |
| **بحث في الويب** | `web_search` بمزوّد يختاره المستخدم (Tavily / Brave / Serper) أو DuckDuckGo مجاناً بلا مفتاح |
| **أدوات git** | `git_status` `git_diff` `git_log` `git_commit` `git_branch` كأدوات محكومة بقواعد الصلاحيات، مع خيار التزام تلقائي بعد كل دورة |
| **ذاكرة المشروع** | اكتب `#ملاحظة` في المحرر (أو دع الوكيل يستخدم `remember`) فتُحفظ في `.freecode/memory.md` وتُقرأ تلقائياً في كل محادثة |
| **إدخال الصور** | الصق صورة (`Ctrl+V`) أو أفلتها على المحرر أو اخترها بزر «صورة» — تُضغط تلقائياً وتُرسل للنموذج متعدد الوسائط (حتى 4 صور، والنموذج يقرأ النص والأخطاء من اللقطة) |
| **مهارات (Skills)** | مجلدات `SKILL.md` بصيغة agentskills.io المفتوحة: يُدرج الوكيل أوصافها في سياقه ويفتح التفاصيل عند الحاجة فقط، وتستدعيها صراحة بـ `/اسم-المهارة` |
| **إضافات (Plugins)** | حزمة واحدة تجمع مهارات + hooks + قواعد + خوادم MCP (`plugin.json` + `skills/`)، في مجلد المستخدم أو المشروع. إضافة المشروع **لا تُفعّل قبل ثقتك**، وأي تعديل عليها يطلب ثقة جديدة (بصمة محتوى) |
| **فحص أمني `/security`** | يفحص مشروعك فعلياً بلا استهلاك نموذج: أسرار مكشوفة في الكود (AWS/OpenAI/GitHub/JWT/كلمات مرور)، ملفات حساسة متتبَّعة في git (`.env`, `id_rsa`, `credentials.json`)، أسرار في تاريخ git، أنماط كود خطرة (`eval`, تعطيل TLS، SQL مركّب)، وثغرات الاعتماديات عبر `npm audit` — مرتّبة بالخطورة مع خطوات إصلاح، و`/security deep` يرسل النتائج للوكيل ليصلحها |
| **وكلاء متوازون (git worktree)** | فوّض حتى 4 مهام مستقلة في وقت واحد: كل وكيل يعمل في **نسخة عمل معزولة** على فرعه الخاص فلا يتعارضون ولا يلمسون مشروعك، ثم تدمج ما تريد أو تتجاهله من لوحة «الوكلاء» (مع بطاقة لكل وكيل: ملفاته، فروقه، سجلّه) |
| **وضع Headless (بلا واجهة)** | نفس الوكيل من سطر الأوامر للـ CI والسكربتات: `freecode -p "المهمة" --yes --json` مع صور وظلّ ملفات معدّلة وسجل أدوات |
| **عزل الأوامر (Sandbox)** | شغّل أوامر الوكيل داخل حاوية Docker/Podman: مشروعك فقط مكشوف في `/work`، وبقية جهازك خارجها. أوضاع: `off` (افتراضي) · `auto` · `docker` · `podman` — والطلب الصريح لمحرّك غائب **يُرفض ولا ينزل خفيةً** إلى جهازك. يُضبط من الإعدادات أو `/sandbox` |
| **ذكاء الكود (LSP)** | أدوات `code_definition` · `code_references` · `code_hover` · `code_diagnostics` عبر خادم اللغة الحقيقي (typescript-language-server / pyright / gopls / rust-analyzer): قفزة دقيقة إلى التعريف، مراجع فعلية، وتشخيصات المحرّك نفسه — مع بديل نصي إن لم يوجد خادم |
| **جسر IDE (VS Code وأي محرّر)** | خادم محلي على `127.0.0.1` برمز: المحرّرات ترسل طلباً وتتابع البث الحي (SSE). إضافة VS Code جاهزة في `ide/vscode` (إرسال السؤال/التحديد + نافذة الحالة) |
| **قياس الموثوقية (`/reliability`)** | أرقام حقيقية بدل الانطباع: نسبة التعديلات التي احتاجت مطابقة متسامحة، فشل التحقق، أكثر الأدوات فشلاً، عدد نقرات الموافقة، ووسيط زمن الدورة. سجل محلي في جهازك فقط ولا يُرسل لأي مكان |
| **تشخيص الأعطال (`/diagnostics`)** | يعرض آخر الأعطال (أوامر فشلت، تحقق فاشل، دورات لم تكتمل) مجمّعة، و`/diagnostics fix` يرسلها للوكيل ليحلّل السبب الجذري لا العَرَض |
| **فحص إغلاق قبل التسليم** | إن فشل التحقق التلقائي بعد تعديلاتك، لا ينهي الوكيل الدورة: يعيد الأخطاء لنفسه مرة أو مرتين ثم يسلّم — فلا يسلّم كوداً مكسوراً بصمت |
| **تقليل النقرات** | زر **«كل تعديلات هذا الملف»** في بطاقة الموافقة: موافقة واحدة تغطي بقية تعديلات الملف في الدورة (وبقية الملفات تبقى تسأل)، مع «وافق على الباقي في هذه الدورة» وقواعد `allow` المحفوظة |
| **تقييم الموديلات (`/models-eval`)** | لا تخمّن أي موديل مجاني أفضل: **14 مهمة كود حقيقية** بمعايير قبول معلنة تُشغَّل محلياً على كل موديل، والحكم من **محاسب مخفي** يفحص سلوك الكود لا كلام الموديل — ثم جدول ترتيب وتوصية بالأرقام (`freecode-eval` في سطر الأوامر، مع `--verify-bank` لفحص سلامة البنك نفسه) |
| **تقييم على أعطال مشروعك (`/models-eval from-project`)** | لا تقييم على بنك عام فقط: تُستخرج المهام من **أعطال مشروعك الحقيقية** في سجل الموثوقية، **والمتكرر منها يتقدّم** («تكرّر 3 مرات — أولوية عالية») فالترتيب بالأهمية لا بالأحدث — والمحاسب يعيد تشغيل الأمر الفاشل نفسه ويحمي ملفات الإعداد ببصمة تمنع «الإصلاح» بتعطيل الفحص |
| **مقارنة A/B (`/ab-test`)** | هل نسخة `FREECODE.md` الجديدة أفضل فعلاً؟ أو هل تستحق **خريطة المستودع** توكناتها؟ شغّل نفس المهام بنفس الموديل بفرق **واحد فقط** — نص التعليمات، أو خيار وكيل (`ctx repoMap` / `ctx autoVerify`) — وقارن النجاح والتوكنات والخطوات، مع **حكم صريح** يحذرك حين تكون العينة صغيرة (`--repeat`) |
| **بطاقة نتائج للمشاركة (`/models-eval share`)** | حوّل تقرير التقييم إلى **بطاقة HTML + شارة SVG + ملصق PNG** (للقنوات التي لا تقبل HTML) — يُرسم الملصق محلياً بخط عربي **مدمج** (تشكيل واتجاه صحيحان بلا HarfBuzz ولا خط نظامي) — أرقام فقط: بلا كود مشروعك وبلا مساراته وبلا أي اتصال شبكي، ومع `--square` يصبح الملصق **مربع 1080×1080** للأفاتار والشبكات |
| **مراجعة الإضافات بموديل ثانٍ (`/plugins install --deep`)** | قبل التثبيت: موديل ثانٍ يقرأ **نصّ** الإضافة (مانيفست + hooks + مقتطفات المهارات) ويشرح ما تفعله فعلاً وما هو مريب — ومع `--model2=<موديل>` يصيران **موديلين متقاطعَين**: حكمان مستقلان، **تُبرز الإشارات المشتركة** (ما أكّده الاثنان) وما انفرد به أحدهما، و**الأشد تحفظاً يفوز**؛ وإذا اختلف الحكمان يستدعي `--model3=<موديل>` **موديلاً ثالثاً محايداً** يفسّر موضع الخلاف ويُعلن **حكم الأغلبية 2 من 3** — **معلومات لا إذن**: فشلها لا يمنع التثبيت ولا يُخفي المراجعة الآلية |
| **لوحة القياس (`/dashboard`)** | الموثوقية وتقييم الموديلات في مكان واحد: نسب النجاح، المطابقة المتسامحة، أكثر الأدوات فشلاً، **اتجاه زمني** للدورات ولجولات التقييم، و«قراءة الأرقام» — توصيات عملية مبنية على أرقامك أنت (`/dashboard export` يصدّر Markdown + JSON، و`freecode --dashboard` في الطرفية) |
| **سوق الإضافات (`/plugins install`)** | تثبيت إضافة من مستودع git بمراجعة أمنية إلزامية قبل التثبيت: يُنزَّل المستودع إلى منطقة مؤقتة ويُعرض محتواه (skills · hooks · قواعد · خوادم MCP) مع كشف الأنماط الخطرة — ولا يُنفَّذ أي شيء من الإضافة أثناء التثبيت. تحديث بمقارنة البصمة، وإزالة إلى سلة قابلة للاسترجاع |
| **جرد الآن من اللوحة** | زرّ «🔁 جرد الآن» أسفل `/dashboard` (و`/dashboard sweep`): يشغّل جرد محاور السياق على مساحة مشروعك مباشرةً بموديلات إعداد الجرد، ويؤرشف ويقارن، **ويعطي إشعار نظام فقط عند انحدار حقيقي** — وينشئ الإعداد تلقائياً من موديلك الحالي إن لم يكن موجوداً |
| **سلسلة الانحدارات (`--timeline`)** | كل الجردات المحفوظة في سلسلة واحدة لكل (موديل × محور): نقاط الفرق عبر الزمن، **تصنيف الاتجاه** (تحسّن/تراجع/متذبذب/ثابت)، أسوأ تراجع بتاريخه، وقائمة الانحدارات — **وكل حدث منسوب لسببه**: تغيّر إعداد الجرد (🧩) أم الموديل نفسه |
| **جرد أسبوعي مؤتمت (`npm run sweep:week`)** | ملف إعداد واحد (`.freecode/sweep.json` — يُنشأ بـ`--init-sweep`) يشغّل الجرد دورياً: أرشفة + مقارنة بالجرد السابق + تقرير مؤرخ + ملصق + كتلة README جاهزة + سطر في `sweep-log.md`، مع `--print-cron` لطباعة سطر crontab (و`schtasks` لويندوز). وملخص آخر جرد يظهر في اللوحة |

## الأدوات

`list_dir` `read_file` `glob` `search` `web_fetch` `web_search` `todo_write` `task` `process_output` و`git_status` `git_diff` `git_log` `code_definition` `code_references` `code_hover` `code_diagnostics` (بدون موافقة) — و`write_file` `edit_file` `run_command` `start_process` `stop_process` `remember` و`git_commit` `git_branch` (بموافقة).
أدوات الملفات محصورة داخل مجلد المشروع (بما في ذلك عبر الروابط الرمزية). `run_command` يعمل بصلاحياتك الكاملة افتراضياً، وحمايته هي الموافقة والقواعد أدناه؛ وإن فعّلت **عزل الأوامر** أدناه صار يعمل داخل حاوية، و`start_process` مثله.

## القواعد والـ Hooks

ملف `rules.json` في مجلد بيانات التطبيق (تحرّره من الإعدادات)، وملف اختياري `.freecode/rules.json` في المشروع بنفس الصيغة:

```json
{
  "permissions": {
    "allow": ["run_command(npm test:*)", "run_command(git status)", "write_file|edit_file(src/**)"],
    "ask":   ["run_command(git push:*)"],
    "deny":  ["read_file(.env*)", "write_file|edit_file(.env*)", "run_command(rm:*)"]
  },
  "hooks": {
    "PreToolUse":  [{ "matcher": "write_file|edit_file", "command": "node scripts/guard.js" }],
    "PostToolUse": [{ "matcher": "write_file|edit_file", "paths": ["**/*.ts"], "command": "npx prettier --write \"$FREECODE_FILE\"" }]
  }
}
```

- **الأولوية:** `deny` ثم `ask` ثم `allow` ثم الإعدادات العامة. `ask` تفرض السؤال حتى مع الموافقة التلقائية، والأمر الخطر يُسأل عنه دائماً حتى لو طابق `allow`.
- **الصيغة:** `الأداة` أو `الأداة(نمط)`، ويمكن جمع أدوات بـ `|`. الأوامر: `npm test:*` بادئة تحترم حدّ الكلمة، و`*` أي نص. الملفات: glob نسبي للمشروع، والنمط بلا `/` (مثل `.env*`) يُطابق اسم الملف في أي مجلد. الروابط: `domain:example.com`. أدوات MCP: `mcp__خادم__*`.
- **الأوامر المركّبة** (`&&` `||` `;` `|` `&`) تُفحص جزءاً جزءاً: لا يُسمح تلقائياً إلا إن سمحت القواعد بكل أجزائها، ويكفي جزء ممنوع لمنع الكل. أي استبدال أوامر (`$(...)`، backticks) أو إعادة توجيه لملف (`>`) أو أقواس يُسقط السماح التلقائي ويُسأل عنه.
- **Hooks:** يصل الـ hook إلى JSON في stdin (`phase` `tool` `args` `result`) ومتغيرات `FREECODE_FILE` (نسبي) و`FREECODE_FILE_ABS` و`FREECODE_COMMAND` و`FREECODE_TOOL` و`FREECODE_PROJECT_DIR`. في `PreToolUse` الخروج بالرمز **2** يمنع الأداة ويصل نص stderr للنموذج؛ أي رمز آخر غير صفري تحذير فقط. في `PostToolUse` أي فشل (مثل lint) يُلحق مخرجاته بنتيجة الأداة فيصلحه النموذج، و`"feedback": true` تلحق المخرجات حتى عند النجاح. إن غيّر الـ hook الملف (تنسيق مثلاً) يُنبَّه النموذج ليعيد قراءته. المهلة الافتراضية 30 ثانية (`timeout`). على ويندوز (cmd) استخدم `%FREECODE_FILE%` بدل `$FREECODE_FILE`.
- **الثقة:** `deny` و`ask` من المشروع تعمل دائماً لأنها تزيد الحماية فقط، أما `allow` والـ hooks فتنفّذ أوامر على جهازك فلا تعمل إلا بعد موافقتك، وتُطلب من جديد إن تغيّر الملف.
- **قواعد الملفات تسري على الأوامر أيضاً:** `deny` و`ask` الخاصة بالمسارات تُطبَّق على وسائط `run_command`، فقاعدة `read_file(.env*)` تمنع كذلك `cat .env` و`node x.js --env=.env`. (تسري على `deny` و`ask` فقط؛ `allow` لا تسمح بأوامر ابدأ.)
- **حدود:** القواعد تحمي من الأخطاء الشائعة وليست sandbox. تبقى حالات لا تُلتقط، مثل بناء المسار داخل برنامج (`cat "$F"` أو سكربت يقرأ ملفاً بمفرده) أو روابط تخفي النطاق (`domain:` خاصة بـ`web_fetch`). للحماية القصوى استخدم `deny` واسعة على الأوامر نفسها.

## التحقق التلقائي وخريطة المستودع

- **التحقق التلقائي** (مفعّل افتراضياً): بعد كل تعديل ناجح يكتشف FreeCode أمر الفحص المناسب من المشروع — سكربت `typecheck` أو `lint` في `package.json`، أو `tsc --noEmit` إن وُجد tsconfig وtypescript، أو `ruff`/`py_compile` لمشاريع بايثون — ويشغّله، ثم يُلحق الأخطاء بنتيجة الأداة فيصلحها النموذج في نفس الخطوة. لا يشغّل الاختبارات الكاملة (بطيئة) — لتلك استخدم `/test`.
  - لا يزيد على فحص واحد كل ثانيتين وثمانية في الدورة، ولا يعمل على ملف غير متعلق بالفحص.
  - حقل «أمر فحص مخصّص» في الإعدادات يستبدل الاكتشاف تماماً، ويمكن تعطيل الميزة كلها.
- **خريطة المستودع**: عند بدء كل رسالة يمسح FreeCode ملفات الكود ويستخرج رموزها (دوال/أصناف/تصديرات) وعلاقات الاستيراد، ثم يرتّب الملفات بترتيب الصفحات (PageRank) على رسم «من يستورد من» ويضيف أعلاها لرسالة النظام. النتيجة: فهم بنية المشاريع الكبيرة بجزء ضئيل من ميزانية السياق (مثل repo map في Aider). تُحسب مرة كل 30 ثانية كحد أقصى.

## العمليات الخلفية

`run_command` له مهلة 120 ثانية، فلا يصلح لخادم تطوير. لذلك:

| الأداة | الوظيفة |
|---|---|
| `start_process` | يشغّل أمراً طويل الأمد في الخلفية (بموافقة) ويعيد معرّفاً |
| `process_output` | يقرأ آخر المخرجات للتأكد أن الخادم جاهز (بلا موافقة) |
| `stop_process` | يوقف العملية (بموافقة) |

`/processes` يعرض العمليات الجارية، وكلها تُقتل تلقائياً عند إغلاق التطبيق.

## عزل الأوامر (Sandbox)

يعزل الأوامر التي يشغّلها الوكيل داخل حاوية، فيبقى مشروعك وحده مكشوفاً في `/work`:

| الوضع | السلوك |
|---|---|
| `off` (الافتراضي) | كما قبل: الأوامر تعمل على جهازك مباشرة، والحماية هي الموافقة والقواعد |
| `auto` | استخدم Docker أو Podman إن وُجد؛ وإلا محلياً مع سبب واضح في السجل |
| `docker` / `podman` | المحرّك المطلوب صراحةً: إن غاب **يرفض الوكيل التنفيذ** ويخبرك (`fatal`) ولا يخفض الحماية بصمت |

```bash
/sandbox                 # الحالة والمحرّكات المتاحة
/sandbox auto            # أو on · docker · podman · off
/sandbox image node:22-bookworm-slim
/sandbox net off         # امنع الشبكة داخل الحاوية
```
أو من **الإعدادات ← عزل الأوامر (Sandbox)**: الوضع، الصورة، الشبكة، ووسائط إضافية مثل `--memory=2g --cpus=2`.

ما تفعله الحاوية: `--rm --init -i`، بـ`--network none` إن أوقفت الشبكة، وتشغيل بمستخدِمك (`--user uid:gid`) فلا تعود الملفات الجديدة مملوكة لـroot، و`--tmpfs /tmp` مع `HOME=/tmp` و`npm_config_cache=/tmp/.npm` (فلا تكتب npm في مجلدك). ويُطبَّق العزل على `run_command` و`start_process` معاً.

## ذكاء الكود (خوادم اللغة)

أدوات لا تقرأ النص فحسب بل تسأل خادم اللغة نفسه:

| الأداة | الفائدة |
|---|---|
| `code_definition` | «أين يُعرَّف هذا الرمز؟» — قفزة دقيقة بدل تخمين بحث نصي |
| `code_references` | كل مواضع الاستخدام (مفيد قبل تغيير واجهة دالة) |
| `code_hover` | نوع المتغير/التوقيع عند موضع ما |
| `code_diagnostics` | أخطاء وتحذيرات الخادم بعد التعديل — نفس ما تراه في محرّرك |

- الافتراضيات: `typescript-language-server --stdio` · `pyright-langserver --stdio` · `gopls` · `rust-analyzer`. ثبّتها عالمياً، مثلاً: `npm i -g typescript-language-server typescript`.
- إعدادك: `<userData>/lsp.json`، وإعداد المشروع: `.freecode/lsp.json` (بنفس صيغة `servers`). إعداد المشروع **لا يُفعَّل قبل ثقتك** لأنه يحدّد أوامر تُنفَّذ على جهازك: `/lsp trust` أو زر «الثقة بإعدادات المشروع» في الإعدادات.
- إن لم يوجد خادم مناسب للغة، تعود الأدوات إلى بحث نصي (`symbolFallback`) وتقول لك ذلك صراحةً.
- الاتصال JSON-RPC على stdio مكتوب هنا مباشرة (بلا مكتبات)، ويحسب أطوال الرسائل **بالبايتات** كما في المواصفة — فالتشخيصات العربية لا تكسر التدفّق.
- المواضع التي تطلبها الأدوات بنظام 1 (كما في المحرّرات) تُحوَّل إلى إحداثيات LSP بنظام 0 داخلياً.
- لو أعاد خادم TypeScript سطر الاستيراد بدل التعريف (سلوك معروف في الأسماء المستعارة)، يقفز المدير مرة واحدة عبر الاستيراد، ويستعين بأمر الخادم `_typescript.goToSourceDefinition` عند الحاجة — فتحصل على موضع التنفيذ الحقيقي.

```bash
/lsp            # حالة الخوادم (متاح/يعمل) وسبب الغياب
/lsp off gopls  # عطّل خادماً بعينه
/lsp trust      # ثق بإعدادات المشروع
```

## جسر IDE (VS Code وأي محرّر)

خادم محلي يفتح نافذة للمحرّرات على نفس الوكيل:

```bash
/bridge              # الحالة
/bridge on           # تشغيل (أو تلقائياً عند الإقلاع من الإعدادات)
/bridge port 4300
/bridge token        # رمز جديد (يُبطل القديم فوراً)
```

| المسار | الوظيفة |
|---|---|
| `GET /status` | حالة الوكيل والمشروع (بلا تشغيل مهمة) |
| `GET /events` | بثّ SSE لكل ما يحدث: نص، أدوات، تعديلات، انتهاء |
| `POST /message` | `{text, allowCommands?, files?}` — يبدأ مهمة ويعيد `202` ثم يأتي الرد على `/events` |
| `POST /abort` | إيقاف المهمة الجارية |

الأمان: الاستماع على `127.0.0.1` فقط، والرمز إلزامي في كل طلب (`x-freecode-token` أو `Authorization: Bearer` أو `?token=`) ويُقارَن بزمن ثابت. و`run_command` عبر الجسر لا يعمل إلا إذا أرسل الطلب `allowCommands: true` **ولم يكن الأمر خطراً**.

إضافة VS Code جاهزة في `ide/vscode`:

| الأمر | ما يفعله |
|---|---|
| `freecode: اسأل FreeCode` | يفتح حقل إدخال ويحمّل السؤال مع سياق الملف/التحديد الحالي |
| `freecode: أرسل التحديد` | يرسل التحديد الحالي فوراً |
| `freecode: الحالة` | يعرض حالة الوكيل والمشروع في نافذة الإخراج |

التثبيت: `cd ide/vscode && npx @vscode/vsce package` ثم ثبّت الـ`.vsix`، أو انسخ المجلد إلى `~/.vscode/extensions/freecode-bridge` وأعد تشغيل VS Code. ثم اضبط `freecode.bridgeUrl` و`freecode.bridgeToken` من إعدادات VS Code (و`freecode.allowCommands` إن أردت السماح بالأوامر).

## git

أدوات مخصّصة (لا عبر shell) فتسري عليها قواعد الصلاحيات نفسها وتظهر لها بطاقة موافقة واضحة:

`git_status` · `git_diff` · `git_log` (بلا موافقة) — `git_commit` · `git_branch` (بموافقة).

`git_commit` لا ينفّذ `push` أبداً ولا يلمس ما لم تحدّده (paths أو `all` أو المُجهّز). وخيار **«التزام تلقائي»** في الإعدادات يلتزم بتغييرات كل دورة برسالة من طلبك — فتصبح كل دورة قابلة للمراجعة والتراجع عبر git.

## بحث الويب

أداة `web_search` (بلا موافقة، فهي قراءة). تعمل **بلا أي مفتاح** عبر DuckDuckGo، فإن أردت نتائج أدق أضف مفتاح Tavily أو Brave أو Serper في الإعدادات. استخدمها لمعرفة إصدارات المكتبات والواجهات الحديثة ثم `web_fetch` لقراءة الصفحة كاملة.

## ذاكرة المشروع

ملف `.freecode/memory.md` يُقرأ تلقائياً في كل محادثة (مثل `FREECODE.md` لكن يتراكم):

- اكتب في المحرر `#المستخدم يفضّل pnpm` ← تُحفظ فوراً بلا استهلاك أي طلب للنموذج.
- أو دع الوكيل يسجّل بنفسه بأداة `remember` (بموافقة، فهي كتابة).
- `/memory` يعرض المحتوى. لا تسجّل فيه ما هو موجود في الكود أو تفاصيل مؤقتة.

## الصور

أربع طرق لإرفاق صورة بالمهمة:

1. **لصق** لقطة شاشة من الحافظة بـ `Ctrl+V` مباشرة في المحرر.
2. **إفلات** ملف صورة على صندوق الكتابة.
3. زر **«صورة»** في شريط الأدوات (اختيار ملف).
4. في الوضع Headless: `freecode -p "..." --image shot.png` (يمكن تكراره حتى 4 مرات).

تُضغط الصورة في المتصفح قبل الإرسال (أقصى ضلع 1600 بكسل، PNG إن كانت صغيرة وإلا JPEG بجودة 0.85) فلا تُثقل الطلب، والحد 4 صور × 6 ميجابايت لكل رسالة. تُحفظ الصور مع المحادثة في مجلد بيانات المستخدم كملفات مستقلة (لا تُخزَّن base64 داخل ملف الجلسة)، وعند استعادة المحادثة يعاد تحميلها، وعند الحاجة للسياق تُسقَط الصور القديمة أولاً قبل النصوص.

## المهارات (Skills)

مهارة = مجلد فيه ملف `SKILL.md` بترويسة `name` و`description` ثم خطوات مكتوبة بلغة طبيعية:

```
.freecode/skills/changelog/SKILL.md   ← مهارة المشروع (تتقدّم)
<مجلد بيانات المستخدم>/skills/...     ← مهاراتك الخاصة في كل مشاريعك
```

```markdown
---
name: changelog
description: يولّد سجل تغييرات من رسائل git ثم يضيفه للملف
---
1. اقرأ `git log --oneline -20`
2. صنّف التغييرات (أُضيف / أُصلح / تغيّر)
3. اكتب CHANGELOG.md بالعربية
```

- الوكيل **لا** يحمّل كل الملفات في السياق: يُدرج الأسماء والأوصاف والمسارات فقط (كشف تدريجي)، ويفتح الملف بأداة قراءة عندما يوافق وصفه المهمة.
- استدعاء صريح: اكتب `/changelog` في المحرر (كل مهارة تصبح أمراً في قائمة `/`)، وما تكتبه بعدها يُمرَّر كوسائط.
- `/skills` تعرض المتاحة، و`/skills new اسم-المهارة` تنشئ قالباً جاهزاً للتحرير.

## الوضع Headless (بلا واجهة)

نفس النواة (الحلقة، الأدوات، القواعد، المهارات، خريطة المستودع، التحقق التلقائي) من سطر الأوامر — مفيد في CI أو السكربتات:

```bash
npm run build
node dist/main/cli.js -p "أصلح فشل الاختبارات" -C /path/to/project --yes --json
```

| الخيار | المعنى |
|---|---|
| `-p, --print <نص>` | المهمة (أو اكتبها على stdin: `echo "..." \| freecode --yes`) |
| `-C, --cwd <مجلد>` | مجلد العمل |
| `-m, --mode <plan\|act>` | خطة للقراءة فقط، أو تنفيذ |
| `-i, --image <ملف>` | إرفاق صورة (يُكرَّر حتى 4) |
| `-y, --yes` | وافق على التعديلات والأوامر غير الخطرة. **بدونها لا يُكتب أي ملف** |
| `--allow-dangerous` | اسمح بالأوامر الخطرة أيضاً (مع `--yes`) |
| `--json` | نتيجة منظّمة: `text` و`tools` و`changedFiles` و`approvals` و`tokens` |
| `--model` / `--base-url` / `--api-key` | تتقدّم على ملف الإعدادات؛ أو `FREECODE_API_KEY` |

الإعدادات تُقرأ من نفس ملف التطبيق. ملاحظة: المفتاح المحفوظ مشفَّراً بـ `safeStorage` لا يمكن فكّه خارج Electron — في CI مرّر `--api-key` أو `FREECODE_API_KEY`. رمز الخروج: 0 نجاح، 1 فشل، 2 خطأ استخدام.

## الوكلاء المتوازون (git worktree)

المهام الكبيرة غالباً مستقلة الأجزاء (اختبارات لوحدة، توثيق، إصلاح تحذيرات في مجلد آخر). بدل تنفيذها واحدة تلو الأخرى، يمكن تشغيل **حتى 4 وكلاء كاتبين في وقت واحد**، كل واحد في نسخة عمل (`git worktree`) على فرع `freecode/…` خاص به:

- **عازلة تماماً**: لا يلمس أي وكيل ملفات مشروعك ولا فروعك، ولا يتعارضون فيما بينهم. تُنشأ النسخ في `<مجلد بيانات المستخدم>/worktrees/…` خارج مشروعك.
- **طريقتان للتشغيل**:
  - من المحادثة: قل «وزّع المهام التالية على وكلاء» — يستخدم الوكيل أداة `delegate` (بطاقة موافقة واحدة تعرض المهام).
  - من الأمر: `/agents أضف اختبارات للوحدة أ` يشغّل وكيلاً واحداً فوراً.
- **لوحة «الوكلاء»** في اللوحة اليمنى: بطاقة لكل وكيل فيها حالته الحيّة (نقطة نابضة أثناء العمل)، ملفاته وعدد أسطره `+أ −ب`، ملخّصه، وسجلّه الكامل بزر «السجل» (يبثّ مباشرةً)، وأزرار **دمج** و**تجاهل** و**الفرق**.
- **الدمج آمن**: يُرفض إن كان عندك تغييرات غير ملتزمة؛ وعند تعارض يُلغى الدمج كاملاً ويُعرض عليك أسماء الملفات المتعارضة — فلا ينتهي المستودع في حالة نصف مدمجة.
- **الصلاحيات داخل الوكلاء**: الكتابة مسموحة تلقائياً (فهي في نسخة معزولة)، أما الأوامر الخطرة (`rm -rf`, `sudo`, …) فتُرفض دائماً وتُسجَّل في البطاقة، وباقي الأوامر تُسمح بلا نقرات. قواعد المنع التي وضعتها في `rules.json` تسري عليهم أيضاً.
- **الحالة تبقى**: بطاقات الوكلاء تُحفظ في `agents.json` وتُستعاد عند إعادة فتح التطبيق، ونسخهم موجودة حتى تدمج أو تتجاهل. `/agents clear` يزيل البطاقات المنتهية.
- أوامر مساعدة: `/agents` (قائمة) · `/agents merge <المعرّف|all>` · `/agents discard <المعرّف|all>` · `/agents clear`.

يحتاج المستودع إلى `git init` والتزام واحد على الأقل؛ وإلا يخبرك الوكيل بذلك بوضوح ويمضي بالتنفيذ المتسلسل العادي.

## الإضافات (Plugins)

إضافة = ملف `plugin.json` + مجلد مهارات (واختيارياً hooks وقواعد وخوادم MCP) في مجلد واحد:

```
plugin.json
skills/review/SKILL.md
```

```json
{
  "name": "Team Pack",
  "description": "مراجعة الكود لدينا",
  "skills": ["skills"],
  "hooks": { "PostToolUse": [{ "matcher": "edit_file|write_file", "command": "npx prettier -w $FILE" }] },
  "permissions": { "allow": ["run_command(npm test:*)"], "deny": ["run_command(curl:*)"] },
  "mcp": { "docs": { "command": "npx", "args": ["-y", "docs-server"] } }
}
```

- **مكانان**: `<بيانات المستخدم>/plugins/<اسم>/` (لكل مشاريعك) و`<المشروع>/.freecode/plugins/<اسم>/` (مع المشروع).
- **الثقة قبل التفعيل**: إضافة المشروع لا تُفعّل hooks/صلاحياتها/خوادمها حتى تكتب `/plugins trust <الاسم>`؛ وأي تغيير في محتواها يُبطل الثقة ويطلب تجديدها (بصمة SHA). هذا يمنع أن يصبح استنساخ مستودع خطراً.
- **الأوامر**: `/plugins` (قائمة بما تحمله كل إضافة) · `/plugins new <اسم>` (قالب جاهز) · `/plugins trust <اسم>` · `/plugins on|off <اسم>`.
- خوادم MCP من الإضافات تُسمّى `الاسم__الخادم` فلا تتعارض مع خوادمك، ومهارات الإضافة تظهر في `/skills` كأي مهارة.

## الفحص الأمني (`/security`)

فحص حقيقي يعمل بلا نموذج (سريع ومجاني)، ثم يقرر الوكيل معك:

```bash
/security          # فحص كامل (ملفات + كود + git + اعتماديات)
/security deep     # نفس الفحص ثم يرسل النتائج للوكيل ليصلح الخطير منها
```

ما يفحصه:

| المجال | أمثلة |
|---|---|
| **أسرار في الكود** | مفاتيح AWS/GitHub/Slack/Google، `sk-…`، JWT، كلمات مرور مكتوبة صراحةً — والقيم تُقنَّع في التقرير فلا تُنسخ إلى السجل |
| **تسريبات git** | `.env` أو `id_rsa` أو `credentials.json` متتبَّع · سرّ ظهر في آخر 50 التزاماً · لا يوجد `.gitignore` |
| **أنماط خطرة** | `eval`/`new Function` · تعطيل تحقق TLS · `StrictHostKeyChecking=no` · SQL مبني بتركيب نصي |
| **الاعتماديات** | ثغرات `npm audit` مع إصدار الإصلاح إن وُجد · الترقيات الرئيسية المتاحة |

النتائج مرتّبة بالخطورة (خطيرة/متوسطة/منخفضة) وكل نتيجة تحمل **خطوة إصلاح محدّدة** وسطرها في الملف.

## الإحصاء والتصدير

- `/stats` — جدول ملخّص للجلسة: عدد الرسائل (لك/للوكيل)، استدعاءات الأدوات وأكثرها استخداماً، الصور، توكنات السياق الآن مقابل الميزانية، والمدة.

## الموثوقية والقياس

الموثوقية ليست شعوراً بل أرقاماً. كل حدث يهم — تعديل، فشل أداة، تحقق، موافقة، دورة — يُسجَّل في `telemetry.jsonl` داخل مجلد بياناتك المحلي (لا يُرسل لأي مكان)، و`/reliability` يلخّصه:

```bash
/reliability          # تقرير: تناسق التعديلات، فشل التحقق، نقرات الموافقة، أزمنة الدورات
/reliability reset    # تصفير السجل
/diagnostics          # آخر الأعطال مجمّعة
/diagnostics fix      # يرسلها للوكيل ليحلّل السبب الجذري ويصلح ما يمكن إصلاحه
```

ما يقيسه بالضبط:

| المقياس | لماذا يهم |
|---|---|
| نسبة المطابقة التامة مقابل **المتسامحة** | المتسامحة تعني أن النموذج أخطأ في نسخ النص القديم؛ ارتفاعها كثيراً تنبيه لجودة السياق |
| فشل التحقق التلقائي | يدل على أخطاء وصلت للنموذج — ومع **فحص الإغلاق** لا تُسلَّم بلا إصلاح |
| أكثر الأدوات فشلاً | يعرف بها ضعف إعداد أو مسار (مثلاً أمر غير مثبّت أو قاعدة عنيدة) |
| عدد نقرات الموافقة | يقيس الإزعاج: كل نقرة يجب أن تكون ذات معنى |
| وسيط/شريحة 95% لزمن الدورة | بطء مفاجئ = أمر معلّق أو خادم لغة يتعثّر |

## تقييم الموديلات (/models-eval)

الموديلات المجانية تتفاوت كثيراً في مهام الكود، والاختيار بالتجربة العشوائية يضيّع وقتاً. هذه الميزة تحسم الأمر بالأرقام:

```bash
/models-eval                          # الموديل الحالي على البنك الكامل (14 مهمة)
/models-eval freellmapi/auto quick    # ثلاث مهام سريعة
/models-eval list                     # بنك المهام مع معايير القبول
/models-eval from-project             # مهام من أعطال مشروعك الحقيقية (ثم تقييم فوري)
/models-eval from-project --list      # اعرض المهام المستخرجة فقط دون تقييم
/models-eval share                    # بطاقة HTML + شارة SVG من آخر تقرير
```

ومن سطر الأوامر (للـ CI والسكربتات):

```bash
freecode-eval --models "freellmapi/auto"                 # يستخدم FREECODE_BASE_URL
freecode-eval --models "موديل1,موديل2@http://127.0.0.1:41802" --out تقرير.md
freecode-eval --list                  # البنك ومعايير القبول
freecode-eval --verify-bank           # فحص سلامة البنك: كل مهمة تفشل قبل الحل وتنجح بعده
freecode-eval --from-project .        # مهام من أعطال مشروعك (سجل الموثوقية المحلي)
freecode-eval --share تقرير.json --out بطاقة.html   # بطاقة مشاركة من تقرير محفوظ (ينتج PNG بجانبها)
freecode-eval --share تقرير.json --png ملصق.png      # ملصق PNG وحده
freecode-eval --models m --out-dir حزمة/             # تقرير md + json + ملصق png في مجلد
```

كيف يُحكم؟ بعد أن ينتهي الموديل من المهمة، نشغّل **محاسباً مخفياً** في ملف خارج مجلد المشروع (فلا يقرؤه الموديل ولا يعدّله) يفحص السلوك فعلاً: يستدعي دوال الكود الخاص به ويقارن النتائج ويشغّل الاختبار. الكلام المعسول لا ينجّح أحداً.

| المهمة | الفئة | ما يقيسه |
|---|---|---|
| `fix-off-by-one` | إصلاح | قراءة اختبار فاشل وإصلاح خطأ حدود في حلقة |

| `multifile-rename` | إعادة هيكلة | إصلاح عدم تطابق مصدَّر بين ملفين في الجهة الصحيحة |
| `write-tests` | اختبارات | كتابة اختبارات حقيقية ≥4 حالات تمرّ فعلاً (ويُفحص سلوكها مستقلاً) |
| `fix-async-order` | تزامن | إصلاح دالة تُعيد قبل انتهاء وعد |
| `parse-csv` | بيانات | محلّل CSV حقيقي: اقتباس، فاصلة داخل حقل، `""` مهربة، CRLF، سطر جديد داخل اقتباس |

التقرير يعطي: نسبة النجاح، التوكنات، متوسط الخطوات للمهمة الناجحة، الزمن، مصفوفة موديل×مهمة، **توصية** («استخدم X لأنه…»)، وأسباب الفشل نصاً. ويُحفظ تلقائياً بصيغتي Markdown وJSON في مشروعك.

> **سلامة البنك نفسه:** `freecode-eval --verify-bank` يختبر كل مهمة مرتين — يجب أن **تفشل** في حالتها الأولى وأن **تنجح** بعد تطبيق حل مرجعي. أي مهمة تنحرف تُكتشف فوراً بدل أن تُحسب على الموديل ظلماً (14/14 مهمة سليمة).

> كل شيء محلي: يحتاج Node فقط، ولا يستهلك إلا التوكنات من خادمك. لا يُرفع أي كود أو تقرير لأي جهة.

## مقارنة التعليمات A/B (/ab-test)

ملفات التعليمات (`FREECODE.md`/`AGENTS.md`) تُكتب عادةً بالذوق، وهذه الميزة تقيس أثرها فعلاً: **نفس المهام، نفس الموديل، نفس الظروف — والفرق الوحيد نص التعليمات.**

```bash
/ab-test c-rules.md                     # الحالي مقابل c-rules.md على المجموعة السريعة
/ab-test c-rules.md --all --repeat 2    # البنك الكامل × جولتان لكل نسخة (للحكم الموثوق)
/ab-test c-rules.md --prompt "أضف دالة جمع مع اختبار"   # مهمة حرة على مشروعك (تحتاج أمر فحص)
/ab-test "اكتب الاختبار دائماً"         # نص مباشر بدل ملف
/ab-test ctx repoMap --repeat 2         # محور سياق: هل الخريطة تستحق توكناتها؟ (مفعّلة مقابل معطّلة)
/ab-test ctx autoVerify                 # محور سياق: هل يُعوّض التحقق التلقائي أخطاء الموديل؟
/ab-test ctx budget                     # ميزانية السياق: واسعة (32k) مقابل ضيقة (8k)
/ab-test ctx memory                     # ذاكرة المشروع: مفعّلة مقابل معطّلة
```

ومن الطرفية:

```bash
freecode-eval --ab قديم.md,جديد.md --models "freellmapi/auto" --quick --repeat 2
freecode-eval --ab قديم.md,جديد.md --models m --prompt "صلح فشل البناء" --out مقارنة.md
```

يعرض التقرير: نجاح كل نسخة، توكناتها، متوسط خطواتها، مصفوفة مهام×نسخة، **حكم صريح** («الجديدة تتفوق: 12/14 مقابل 9/14…») — وإذا كان الفرق لا يُعتد به يقول ذلك بصراحة بدل التجميل، ويذكّرك أن جولة واحدة قد تكون ضجيجاً فكرّر. وفي محاور السياق يُبنى الفرق من **خيار وكيل واحد** (repoMap/autoVerify) ونصوص التعليمات تبقى كما هي، ويصرّح التقرير بذلك (وسم `kind` في JSON). الترتيب يُعكس بين التكرارات إنصافاً، ولا يُعدَّل أي ملف تعليمات فعلي — النسخ تُحقن في الجلسة فقط.

### جرد محاور السياق (`--ctx-sweep`)

سؤال «أُبقي هذه الميزة أم أطفئها؟» يتكرر مع كل موديل جديد، فصار يُقاس دفعة واحدة: **كل موديل × كل محور** — نفس المهام ونفس التعليمات، والفرق خيار وكيل واحد فقط، وترتيب التشغيل يُعكس بين التكرارات، والحكم من محاسب مخفي لا من كلام الموديل.

```bash
freecode-eval --ctx-sweep --models "m1,m2" --quick        # كل المحاور على المجموعة السريعة
freecode-eval --ctx-sweep --axes repoMap,budget --full    # محاور محددة على البنك الكامل
freecode-eval --ctx-sweep --from-project . --repeat 2     # على مهام مبنية من أعطال مشروعك
freecode-eval --ctx-sweep --save                          # أرشفة النتيجة في .freecode/ctx-sweep.jsonl
freecode-eval --ctx-sweep --compare                       # ما تغيّر منذ آخر جرد محفوظ؟
freecode-eval --ctx-sweep --badge جرد.png                 # ملصق PNG للنتيجة (ومع --square يصير مربعاً 1080)
freecode-eval --init-sweep                                # أنشئ .freecode/sweep.json مرة واحدة
freecode-eval --ctx-sweep --save                          # بعدها يكفي: الموديلات والمحاور من الإعداد
freecode-eval --ctx-sweep --table-out جدول.md             # كتلة README مولَّدة آلياً (بعلامتي بداية/نهاية)
freecode-eval --ctx-sweep --verify-cmd "npm run typecheck" # فحص حقيقي لمحور autoVerify بعينه
freecode-eval --ctx-sweep --timeline                      # سلسلة الانحدارات من كل الجردات المحفوظة (عرض فقط)
freecode-eval --ctx-sweep --save --compare --timeline      # جرد جديد + مقارنة + سلسلة محدَّثة
```

المحاور الأربعة: `repoMap` · `autoVerify` · `budget` (واسعة 32k مقابل ضيقة 8k) · `memory` (ذاكرة المشروع مفعّلة/معطّلة). الجدول يُذيَّل بـ**خلاصة عبر الموديلات** لكل محور مع توصية صريحة («أبقِه»/«أطفئه»/«قرّر لكل موديل»)، وبحواشٍ تشرح دلالة العمودين في الميزانية والذاكرة.

**محور `autoVerify` يقيس فحصاً حقيقياً لا ادّعاءً:** النسخة المفعّلة تشغّل أمر فحص فعلي بعد كل تعديل — أمر مشروعك (`verifyCommand` في الإعداد أو `--verify-cmd`)، وإلا الفحص المكتشف داخل المهمة نفسها (`node test.js` · `tsconfig` · `package.json`). ولا يُقاس المحور إلا على المهام التي فيها فحص فعلي، ويُطبع عددها صراحةً («N من M مهمة فيها فحص فعلي»)؛ وإن لم يوجد فحص أصلاً يُستبعد المحور برسالة تشرح السبب — **بلا قياس وهمي وبلا «لا فرق» كاذبة**.

نموذج من قياس فعلي (موديلان وهميان محليان — الغرض إثبات المنهجية، والقراءة الحقيقية تأتي من موديلاتك):

| الموديل | المحور | مفعّل: نجاح | مفعّل: توكن | معطّل: نجاح | معطّل: توكن | فرق النجاح | فرق التوكنات | القراءة |
|---|---|---|---|---|---|---|---|---|
| مستقل | repoMap | 1/1 | 241 | 1/1 | 219 | 0 | أغلى بـ10% | لا مكسب في النجاح وتكلفتها توكنات أعلى — أطفئها |
| مستقل | autoVerify | 1/1 | 219 | 1/1 | 219 | 0 | = | لا فرق يُذكر — القرار ذوقي |
| متردد | repoMap | 0/1 | 257 | 0/1 | 235 | 0 | أغلى بـ9% | لا مكسب في النجاح وتكلفتها توكنات أعلى — أطفئها |
| متردد | autoVerify | 1/1 | 1668 | 0/1 | 235 | +1 | أغلى بـ610% | الميزة مفيدة: نجاح أعلى (وتكلّف توكنات أكثر) |

الخلاصة في هذا النموذج: **خريطة المستودع** يكلّف بلا مكسب عند 2 (من 2 موديل) — «أطفئه»، و**التحقق التلقائي** مفيد عند 1 · بلا فرق عند 1 — «أبقِه». الصف الأخير هو الفائدة الحقيقية: موديل «متردد» كان يفشل بلا فحص، ولمّا رأى مخرجات `node test.js` الفاشلة أصلح خطأه — فصار المحور يفرّق فعلاً بين موديل يحتاج الفحص وموديل لا يحتاجه.

ومع التكرار: `--save` يؤرشف كل جرد في `.freecode/ctx-sweep.jsonl`، و`--compare` يطبع «ما تغيّر منذ آخر جرد» (Δفرق النجاح وΔنقاط التوكنات لكل موديل×محور) ويوسم **الانحدار بتحذير** — فتكشف أثر ترقية موديل أو تغيير إعداد خلال ثوانٍ.

**وسلسلة الانحدارات (`--timeline`) تجيب السؤال الأهم: هل هذا تراجع حقيقي أم تذبذبة واحدة؟** كل جرد محفوظ يُخزَّن معه **وصف إعدادُه وبصمته** (`signature` و`configHash`)، فتبني السلسلة جدولاً لكل (موديل × محور) عبر كل الجردات:

```
| الموديل | المحور | السلسلة (الأقدم ← الأحدث) | الاتجاه | أسوأ تراجع | آخر قراءة |
| متذبذب | autoVerify | +1 → +1 → 0 → 0 | تراجع | −1 (2026-10-13 17:35) | لا مكسب في النجاح… |
```

ويُلحق بها **قائمة الانحدارات** وكل حدث منسوب لسببه بلا تخمين: `🧩 إعداد الجرد نفسه منذ الجرد السابق — كل فرق في الأرقام يُنسب إلى الموديل/المهام`، أو `🧩 إعداد الجرد تغيّر منذ آخر جرد: … ← …` عند تغيير الإعداد. و`--timeline` وحده (بلا موديلات وبلا أعلام حفظ) يعرض الأرشيف فقط بلا قياس جديد.

**صدق المحاور:** إن كان محور `memory` مطلوباً ولا يوجد `.freecode/memory.md` في المجلد، يُطبع تنبيه صريح أن الصف سيكون «بلا فرق» **بحكم غياب الملف لا بحكم الموديل** — فلا يُقرأ الصمت كأنه نتيجة.

**وتشغيله أسبوعياً بأمر واحد:**

```bash
npm run sweep:week                 # من إعداد المشروع: جرد + أرشفة + مقارنة + تقرير + ملصق + سجل
npm run sweep:week -- --print-cron # اطبع سطر crontab (وسطر schtasks لويندوز) والصقه مرة واحدة
```

ينتج في `.freecode/sweeps/` تقريراً مؤرخاً وملصقاً وكتلة README جاهزة، ويضيف سطراً إلى `.freecode/sweep-log.md`، ويظهر ملخص آخر جرد (مع تحذير الانحدار إن وُجد) في قسم «جرد محاور السياق (المحفوظ)» داخل `/dashboard`.

## بطاقة النتائج القابلة للمشاركة

لحظة تصل إلى نتيجة تستحق النقاش (اختيار موديل لفريقك، أو أثر قاعدة جديدة)، حوّلها إلى بطاقة:

```bash
/models-eval share        # بعد أي تقييم — يكتب في .freecode/ بطاقة HTML + شارة SVG + ملصق PNG
freecode-eval --share تقرير.json --out بطاقة.html   # من تقرير محفوظ (ومعها ملصق PNG)
freecode-eval --share تقرير.json --png ملصق.png      # الملصق وحده
freecode-eval --share تقرير.json --png مربع.png --square   # مقاس مربع 1080×1080 (أفاتار/شبكات)
```

البطاقة: صفحة HTML عربية (RTL) مكتفية بذاتها — بلا خطوط أو موارد خارجية، تُفتح في أي متصفح بلا إنترنت — فيها جدول الترتيب، مصفوفة مهام×موديل، التوصية، وأسباب الفشل. والشارة SVG صغيرة تُلصق في README. **والملصق PNG** صورة جاهزة للنشر (القنوات التي لا تقبل HTML): يُرسم بكود محلي — قارئ TrueType مصغّر + تشكيل عربي (اختيار أشكال العرض ووصل «لا») + ترتيب ثنائي الاتجاه + مُرمِّز PNG — بخط مدمج (Debian Vera بترخيص حر) فلا يعتمد على أي خط نظامي. **تحتوي أرقاماً فقط**: لا كود من مشروعك ولا مساراته ولا مفاتيح — وهذا منصوص عليه داخل البطاقة نفسها.

## لوحة القياس (/dashboard)

تجمع الموثوقية والتقييم في تقرير واحد قابل للتصدير:

```
/dashboard            # اللوحة كاملة في المحادثة
/dashboard export     # تصدير .freecode/dashboard-<تاريخ>.md و .json
freecode --dashboard  # في الطرفية (JSON مع --json)
```

تشمل: نسب نجاح الدورات، المطابقة المتسامحة مقابل التامة، أخطاء الأدوات الأكثر تكراراً، عدد الموافقات المطلوبة، أزمنة الدورة (وسيط والشريحة 95%)، **خط اتجاه** للدورات الأخيرة وخُط ثانٍ لنسبة نجاح متصدّر الموديلات عبر جولات التقييم، ثم قسم «قراءة الأرقام» الذي يربط كل رقم بإجراء عملي (مثال: ارتفاع المطابقة المتسامحة ⇒ اطلب قراءة الملف قبل التعديل). سجل الجولات محلي في `eval-history.jsonl` ومحدود بـ60 جولة.

وتحت قسم الجرد في اللوحة يأتي قسم **«سلسلة الانحدارات عبر الجردات»** بالمخطط والانحدارات نفسها (ويُصدَّر في JSON داخل `sweepTimeline`).

**من اللوحة نفسها** أزرار أسفل التقرير: «🔁 جرد الآن (جرد محاور السياق)» و«🎴 صدّر ملصق آخر جولة PNG» و«🗂 تصدير اللوحة md+json» (أو `/dashboard sweep` و`/dashboard badge`). زرّ الجرد يشغّل القياس محلياً على مساحة مشروعك (بمحرك Node المدمج في التطبيق) بموديلات `.freecode/sweep.json` — وينشئ الإعداد من موديلك الحالي إن لم يكن موجوداً — ثم يؤرشف ويقارن، **ويُرسل إشعار نظام فقط عند انحدار حقيقي** (بلا ضجيج عند التحسّن أو الثبات). الملصق يحمل **اسم مشروعك** و«شعاره» (حرف ملوّن مشتق من الاسم — بلا ملفات خارجية) ونتيجة أفضل موديل في آخر جولة تقييم، ويُكتب في `.freecode/last-round-badge-<ختم>.png`.

وإن وُجدت أعطال موسومة **بيئياً** (أداة ناقصة، صلاحية، منفذ مشغول، شبكة، مساحة قرص…) يظهر لها قسم مستقل «🌐 أعطال بيئية» بعدّها **وخطوة إصلاح مقترحة** لكل نمط، ويُذكر عددها في الملخص السريع — لأن هذه لا تُصلح بتعديل ملفات المشروع، وتُوسم كذلك في مهام `--from-project` («🌐بيئي») وتُرتَّب بعد ما يُصلح بالكود.

## سوق الإضافات (/plugins install)

```
/plugins install https://github.com/user/plugin-repo   # تنزيل + مراجعة (لا تثبيت)
/plugins install https://github.com/user/plugin-repo --yes
/plugins install ./plugin-dir --deep   # + مراجعة دلالية بموديل ثانٍ قبل التثبيت
/plugins install ./plugin-dir --deep --model2=moodel-b   # موديلان متقاطعان: تقاطع الإشارات والأشد تحفظاً يفوز
/plugins install ./plugin-dir --deep --model2=m --model3=محكّم   # وعند اختلاف الحكمين: موديل ثالث محايد يفسّر الخلاف ويُعلن الأغلبية
/plugins update <الاسم> [--yes] · /plugins remove <الاسم> · /plugins installed
```

سير العمل مقصود أن يكون **خطوتين**: التنزيل إلى منطقة مؤقتة ثم عرض تقرير مراجعة (الاسم، الإصدار، عدد الملفات، المهارات، أوامر `hooks` كما ستُشغَّل حرفياً، قواعد الصلاحيات، خوادم MCP، وتصنيف مخاطر: منخفض/متوسط/خطير مع كشف أنماط مثل `rm -rf` و`curl | sh` و`sudo`)، ثم تثبيت صريح بـ`--yes`. أبداً لا نُشغّل أي شيء من الإضافة أثناء التثبيت: لا `npm install` ولا سكربتات ولا hooks. النسخة السابقة تُنقل إلى نسخة احتياطية عند الاستبدال، والإزالة إلى سلة قابلة للاسترجاع، ولا يُحفظ مجلد `.git` في الإضافة المثبّتة.
